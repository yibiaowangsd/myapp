# 1.7.1 启动与再次进入性能优化

基线：1.7.0，`c12b5f3783f1128cf936f80efccee695589fd0a5`。本次根据启动调用链定位重复工作；尚未获得目标手机的启动跟踪，因此不宣称具体秒数或提速百分比。

## 已确认的代码问题与修改

| 原路径 | 1.7.1行为 |
| --- | --- |
| ViewModel初始化先探测来源；onResume另外探测，再启动包含探测的刷新 | 首屏先读取加密数据库中已生成的日视图，同步等待首屏数据就绪后再进行 |
| 刷新互斥锁包住来源补采，补采超时为20秒 | 外部来源查询移出界面刷新锁，切日与本地阅读无需等待整轮补采 |
| 每次刷新都强制重建日视图，首次无缓存时可能连续构建两次 | 最近3天的进程内缓存按数据版本、策略代次失效，当天最多复用30秒；跨日也会失效 |
| 只要日期包含任意排除记录，旧快照路径就重新计算 | 新快照记录生成时的策略代次；策略未变时可以安全直接展示，策略变化后拒绝旧快照 |
| build内部推导事件后，持久化再推导一次 | 同一次构建共享事件结果；利用已读的片段表减少逐条查询 |
| 每次刷新加载位置点、地点与运行日志 | 位置点在完整时间线页加载，趋势在趋势页加载，运行日志在设置页加载；移除未使用的地点查询 |
| 每张照片都调用MediaStore.getVersion | 每轮扫描仅查询一次；照片内容与原索引规则不变 |
| stableId与来源键为每个字节创建格式化对象 | 直接编码小写十六进制，保持SHA-256/HMAC输入、截断长度及输出完全一致 |
| 每次onStop清空图片缓存 | 保留有24MB上限的LRU缓存；UI隐藏本身不清空，收到内存压力通知时裁减/清空；串行加载取得许可后复查缓存 |

Health Connect权限探测增加1.5秒等待上限，超时标记为未知，避免可选健康服务拖住其他来源的状态更新。首次初始化没有可用日视图时仍需完成一次本地构建；首次大量数据导入、加密数据库打开以及系统进程启动仍存在实际开销。

## 正确性与升级

- 已保存的日视图仍位于SQLCipher数据库，不写入明文启动缓存。
- 修改记录范围、排除应用或删除记录会使旧策略快照失效；新增观察、修正、来源状态变化会使进程内结果失效。
- 日视图缓存最多3项；当天30秒到期或跨日后重新计算，不以缓存替代采集。
- 保留手动刷新、系统权限流程、后台记录和失败重试；未通过删记录、去照片或隐藏成就来提速。
- 版本1.7.1，versionCode12，沿用个人Release签名与Room V1，可覆盖同签名旧版。

本次Release构建通过；93项core测试与92项app测试通过，共185项。Release Lint为0个错误、29个警告。APK签名、ZIP及原生库16KB对齐检查通过，签名证书与1.7.0一致，debuggable关闭。新增回归覆盖缓存命中不读取原始观察、策略变化拒绝旧快照、新数据与删除失效、跨日/TTL/容量回收、内存压力下的缩略图回收、所有字节的编码等价性，以及共享事件结果的日视图一致性。
